
- 下拉框固然要使用过滤后的字典副本
- 保存一层全量的字典查询结果
- 并在查询时做一层拦截防护，组织用户查到下拉框所含的过滤字典副本之外、全量字典查询结果之中的结果

在前端工程化中，叫做 **“展示数据（全量）” 与 “交互选项（视图子集）” 解耦**。

### 三位一体的最佳实践

一个成熟、健壮的企业级列表页面，这三者的职责是分工明确的：

|层级|动作|解决的核心问题|
|---|---|---|
|**下拉选项 (`formData.options`)**|仅保留 2（B品）和 3（C品）|**引导正确输入**：从源头杜绝用户去查 1 和 4|
|**请求拦截 (`query() 校验`)**|强制必填，非空拦截|**防御性保底**：防止用户清空选项导致全库数据泄露/崩溃|
|**表格翻译 (`dictMap / formatter`)**|保留全量字典（含 1~4）或做好原值兜底|**数据容错**：万一历史数据混入了 1 或 4，也能正常翻译或显示，绝不白屏或变破折号|

### 字典（Dict）机制总结

#### 一、字典是什么

系统内置的**通用枚举数据管理机制**，采用两级树形结构：

```text
字典分类（一级，携带分类 ID，UUID）
└── 字典项（子级，携带 code + name + sort，可继续嵌套下级）
```

- **分类**：一类选项的容器，按业务语义划分，如“XX状态”“XX类型”。
- **字典项**：具体选项，数据结构通常为 `{ code: 值, name: 显示文本 }`，供页面下拉选择或数据翻译使用。

维护入口位于 **系统管理 → 字典管理** 页面，可对字典分类和字典项进行增删改查，无需重新发布代码即可调整选项。

#### 二、API 层

| 函数 | 接口 | 用途 |
| --- | --- | --- |
| `get(ids)` | `dict/list` | 传入**分类 ID 数组**，返回对应选项列表，最常用 |
| `get2(data)` | `dict/get2` | 另一种字典查询接口，当前项目暂未发现实际使用 |
| `list(data)` | `dict/page` | 字典管理页分页查询 |
| `add / edit / del` | `dict/create` / `dict/edit` / `dict/delete` | 字典管理页 CRUD |
| `getArea(data)` | `area/list` | 区域列表查询，与字典接口定义在同一文件中 |

#### 三、前端三种使用模式

##### 模式 A：单分类查询 → 直接赋值

```js
get(["分类ID"]).then((res) => {
  if (res.code == 0) {
    this.formData.xxx.options = res.data || [];
    // res.data = [{ code, name, ... }]
  }
});
```

##### 模式 B：多分类一次请求 → 扁平数组按 `parentId` 拆分

```js
get([分类ID1, 分类ID2, ...]).then((res) => {
  // res.data 为所有分类的字典项拼接后的大数组，每一项都带 parentId

  this.list1 = _.filter(res.data, { parentId: 分类ID1 });
  this.list2 = _.filter(res.data, { parentId: 分类ID2 });
});
```

> ⚠️ **注意：两种模式的返回值使用方式不同。** 单分类查询时，可直接将 `res.data` 作为该分类的选项数组使用；多分类查询时，`res.data` 为多个分类字典项拼接后的扁平数组，需要根据 `parentId` 过滤并拆分。

##### 模式 C：分类 ID 的管理方式

- **推荐**：将字典分类 ID 集中定义在常量文件中，并使用语义化命名，方便复用、维护和环境切换。
- **避免**：在不同业务页面中散落硬编码 UUID。

#### 四、字典数据的消费点

1. **查询表单下拉**

   使用 `options` 配合：

   ```js
   prop: {
     value: "code",
     label: "name"
   }
   ```

   将字典数据渲染为 `select` 下拉选项。
2. **表格列翻译**

   在 `formatter` 中根据 `code` 查找对应的 `name`：

   ```js
   options.find((v) => v.code == cellValue)?.name || "-"
   ```

   将后端返回的字典 `code` 转换为用户可读的中文名称。
3. **详情页翻译**

   在跳转详情页或组装详情数据前，根据字典列表将 `code` 替换或转换为对应的 `name` 后再传入。

#### 五、规范与注意事项

1. **成功判断**

   接口请求成功统一以：

   ```js
   res.code == 0
   ```

   为判断条件。由于 `res.data` 可能为空，建议使用：

   ```js
   res.data || []
   ```

   进行兜底，避免后续遍历或赋值时报错。
2. **ID 环境敏感**

   字典分类 ID 为 UUID，并且可能随开发、测试、生产等不同数据库环境发生变化，因此应集中管理分类 ID，避免直接散落在业务代码中，以便后续统一切换和维护。
3. **数据分层**

   查询表单条件使用的字典数据建议放在表单相关数据结构中；仅用于表格、详情等展示场景的字典数据建议单独存放，避免污染表单配置和渲染逻辑。
4. **新增字典低改码**

   对于现有页面已经通过分类 ID 动态查询字典项的场景，如果只是新增、删除或调整该分类下的字典项，一般只需在 **系统管理 → 字典管理** 页面维护数据即可，无需修改或重新发布前端代码。
5. **废弃代码**

   项目中个别历史工具类引用的接口已经不存在，并标注有“暂时无法使用”等说明，此类代码视为废弃逻辑，后续开发中不要继续复用。
