# 应用构建范式：客户端—服务端系统的主流应用模型

> 目标：建立一张“应用到底是怎么跑起来的”全景地图。  
> 重点不是死记技术名词，而是理解：**谁发起动作、数据怎么流动、逻辑在哪里执行、状态存在哪里、组件之间怎么通信。**

---

## 0. 先从最简单的模型出发

最经典的全栈应用，可以先粗暴理解为：

```text
用户
 ↓
客户端（Web / App / 桌面程序）
 ↓ HTTP 请求
服务端
 ↓
业务逻辑
 ↓
数据库
 ↓
返回结果
 ↓
客户端更新界面
```

例如一个后台管理系统：

```text
Vue
 ↓
POST /api/users
 ↓
Spring Boot
 ↓
Controller
 ↓
Service
 ↓
Mapper
 ↓
MySQL
```

本质上就是：

```text
客户端提出一个业务要求
        ↓
服务端处理业务
        ↓
读写数据 / 调用其他系统
        ↓
把结果返回客户端
```

这个模型非常重要，但它只是应用构建中的一条主干。

真实系统还会出现：

```text
请求驱动
事件驱动
消息驱动
实时推送
后台任务
流式处理
点对点通信
边缘计算
本地优先
AI 工作流
……
```

---

# 一、理解应用架构前，先区分三个概念

很多初学者容易把 REST、微服务、WebSocket、Serverless 放在同一个层级比较，实际上它们不是一类东西。

## 1. 应用架构 / 构建范式

回答的是：

> 整个系统怎么拆、逻辑放在哪里、组件之间是什么关系？

例如：

- 三层架构
- 单体架构
- 微服务
- 事件驱动架构
- Serverless
- P2P
- Local-first

---

## 2. 通信模型 / 协议

回答的是：

> 两个组件怎么说话？

例如：

- HTTP
- REST
- GraphQL
- RPC / gRPC
- WebSocket
- SSE
- TCP / UDP
- 消息队列

所以：

```text
微服务
```

可以内部使用：

```text
REST
gRPC
MQ
```

而不是说：

```text
REST vs 微服务
```

它们根本不是同一个层级。

---

## 3. 基础设施组件

回答的是：

> 系统借助什么完成某种能力？

例如：

- MySQL：持久化数据
- Redis：缓存 / 分布式状态
- Kafka：消息 / 事件流
- RabbitMQ：消息队列
- Nginx：反向代理
- CDN：静态资源分发
- Elasticsearch：搜索
- 对象存储：文件、图片、视频

这些通常是架构中的“零件”，而不是整个架构本身。

---

# 二、模型 1：经典 Client / Server

这是几乎所有网络应用最基础的模型。

```text
Client
  ↓
Server
  ↓
Data
```

Client 可以是：

```text
浏览器
手机 App
微信小程序
桌面软件
游戏客户端
IoT 设备
命令行程序
```

Server 可以是：

```text
Spring Boot
Node.js
Go
.NET
Python
Rust
```

核心思想：

> 客户端负责交互，服务端负责提供能力。

例如：

```text
App → 登录请求 → Server
App ← 用户信息 ← Server
```

这是后面绝大多数模式的基础。

---

# 三、模型 2：三层 / N-Tier 架构

这是企业应用中非常经典的架构思想。

最基本的三层：

```text
Presentation Tier
展示层
   ↓
Application / Logic Tier
业务逻辑层
   ↓
Data Tier
数据层
```

对应一个 Web 项目：

```text
Vue
 ↓
Spring Boot
 ↓
MySQL
```

继续细拆 Spring Boot：

```text
Controller
 ↓
Service
 ↓
Mapper / Repository
 ↓
Database
```

所以你之前学到的：

```text
Controller
Service
Mapper
DTO
VO
Entity
```

本质上是在三层架构内部继续进行职责拆分。

## 适合

- 企业后台
- 信息管理系统
- 电商后台
- ERP / CRM
- 中小型 Web 应用
- 普通业务系统

## 最重要的理解

三层架构不是说系统一定只有三台服务器。

它表达的是：

> **职责分层。**

AWS 至今仍把三层 / 多层架构描述为用户型应用中的经典、常见基础模式。

---

# 四、模型 3：单体应用（Monolith）

单体的意思不是“代码写得乱”，而是：

> 整个后端通常作为一个整体开发、构建和部署。

例如：

```text
Vue
 ↓
Spring Boot
 ├── user
 ├── order
 ├── product
 ├── payment
 └── auth
 ↓
MySQL
```

最终：

```text
mvn package
       ↓
app.jar
       ↓
一整个部署
```

用户模块、订单模块、商品模块虽然代码分开，但仍属于同一个应用。

---

## 模块化单体（Modular Monolith）

这是非常值得学习的一种方式：

```text
Application
├── user module
├── order module
├── product module
├── payment module
└── auth module
```

仍然：

```text
一个应用
一个部署单元
```

但是内部边界清晰。

对于个人项目、校招项目和大量中小企业项目，它通常比一上来就搞微服务合理得多。

---

# 五、模型 4：API 驱动的前后端分离

这是现代 Web / App 开发中最常见的应用形式之一。

```text
Web
Mobile App
Mini Program
Desktop
     ↓
    API
     ↓
Backend
     ↓
Database
```

客户端不关心后端内部怎么实现，只认 API。

例如：

```http
GET /users/1
POST /orders
DELETE /cart/3
```

最常见的是：

```text
HTTP + JSON
```

---

## REST

典型：

```text
GET    /users
GET    /users/1
POST   /users
PUT    /users/1
DELETE /users/1
```

很适合普通 CRUD 和 Web API。

---

## RPC / gRPC

思维更接近：

```text
客户端直接调用远程函数
```

例如：

```text
userService.getUser(1)
```

看起来像调用本地方法：

```text
getUser(1)
```

实际上：

```text
Client
 ↓ network
Remote Server
 ↓
getUser()
```

gRPC 常用于：

- 微服务之间调用
- 内部系统
- 多语言分布式服务
- 低延迟、高吞吐通信

---

## GraphQL

思路是：

> 客户端描述“我到底想拿哪些字段”。

而不是后端为每一种页面提前设计大量固定接口。

因此：

```text
REST
RPC
GraphQL
```

更多是在讨论：

> **客户端和服务端 API 怎么设计。**

而不是整个系统的部署架构。

---

# 六、模型 5：BFF（Backend for Frontend）

当一个系统同时有：

```text
Web
iOS
Android
小程序
大屏
```

不同客户端需要的数据可能完全不同。

传统：

```text
Web ────┐
App ────┼──→ 一个通用 Backend
小程序 ─┘
```

可能导致后端 API 越来越复杂。

BFF：

```text
Web
 ↓
Web BFF
   \
    → Core Services

Mobile
 ↓
Mobile BFF
   /
```

也就是：

> 给不同类型的客户端准备更适合它自己的后端入口。

例如手机端希望：

```text
一次请求拿完整首页
```

Web 后台却希望：

```text
大量细粒度查询
```

BFF 就可以分别优化。

---

# 七、模型 6：API Gateway + 后端服务

随着后端越来越复杂，客户端一般不会直接知道几十个服务在哪里。

而是：

```text
Client
   ↓
API Gateway
   ↓
 ┌───────────────┐
 │ User Service  │
 │ Order Service │
 │ Pay Service   │
 │ Search Service│
 └───────────────┘
```

Gateway 常负责：

```text
路由
认证
限流
日志
协议转换
负载均衡
统一入口
```

因此你以后看到：

```text
Client → Gateway → Services
```

不要觉得奇怪。

Gateway 本质上像：

> 整个服务端系统的大门。

---

# 八、模型 7：微服务（Microservices）

单体：

```text
Backend
├── 用户
├── 订单
├── 商品
└── 支付
```

微服务：

```text
User Service
Order Service
Product Service
Payment Service
```

每一个都是：

```text
独立程序
独立部署
独立扩缩容
```

典型架构：

```text
Client
  ↓
API Gateway
  ↓
┌─────────────┐
│ User Service│──→ User DB
│ Order       │──→ Order DB
│ Product     │──→ Product DB
│ Payment     │──→ Payment DB
└─────────────┘
```

服务之间可能使用：

```text
HTTP
gRPC
MQ
Event Bus
```

---

## 为什么微服务存在？

大型项目中：

```text
所有代码
所有团队
所有功能
```

都塞进一个应用会越来越难维护。

于是按照业务能力拆：

```text
用户
订单
库存
支付
物流
优惠券
搜索
推荐
```

各自独立演进。

---

## 微服务不是“更高级的单体”

它会引入大量额外问题：

```text
服务发现
网络通信
超时
重试
分布式事务
数据一致性
链路追踪
服务治理
容器部署
配置中心
消息队列
```

所以：

> **小项目不要为了“高级”而微服务化。**

---

# 九、模型 8：同步 Request / Response

这是你目前最熟悉的模式。

```text
Client
 ↓ request
Server
 ↓ process
Database
 ↓
Server
 ↓ response
Client
```

例如：

```text
用户点击“查询”
 ↓
GET /orders
 ↓
查询数据库
 ↓
返回订单列表
```

特点：

> 调用方通常等待结果。

非常适合：

- 查询
- CRUD
- 登录
- 普通业务操作
- 需要立即给用户结果的请求

---

# 十、模型 9：异步任务 / Web-Queue-Worker

有些任务不适合让用户一直等。

例如：

```text
生成 500 页 PDF
导出 100 万条 Excel
转码视频
批量发送邮件
AI 长任务
```

如果：

```text
Client
 ↓
Server
 ↓
处理 5 分钟
 ↓
Response
```

体验会很差，也很容易超时。

于是：

```text
Client
 ↓
Web Server
 ↓
创建任务
 ↓
Queue
 ↓
Worker
 ↓
真正执行
```

Web Server 可以快速告诉客户端：

```json
{
  "taskId": "123",
  "status": "processing"
}
```

随后：

```text
Worker
 ↓
完成任务
 ↓
更新状态
```

客户端再查询：

```text
GET /tasks/123
```

或者由服务端主动通知。

---

## 常见技术

```text
RabbitMQ
Kafka
Redis Queue
SQS
Celery
BullMQ
XXL-JOB
```

Azure 将这种模式专门总结为：

```text
Web → Queue → Worker
```

它是现代后台任务非常典型的应用模式。

---

# 十一、模型 10：事件驱动架构（Event-Driven Architecture）

这是从“调用别人”转变成：

> **告诉系统：某件事情发生了。**

传统：

```text
Order Service
 ↓
直接调用 Inventory
 ↓
直接调用 Coupon
 ↓
直接调用 Notification
```

订单服务必须认识所有人。

事件驱动：

```text
Order Service
 ↓
发布：
OrderCreated
 ↓
Event Bus / MQ
 ↓
├── Inventory Service
├── Notification Service
├── Analytics Service
└── Coupon Service
```

订单服务只需要说：

> 订单创建了。

至于谁关心，由订阅者自己决定。

---

## 三个核心角色

```text
Producer
生产事件
   ↓
Broker / Event Bus
事件通道
   ↓
Consumer
消费事件
```

AWS 和 Azure 都把这种模式作为现代分布式系统的重要架构模式。

---

## 为什么重要？

因为可以降低耦合：

```text
Producer
```

不需要知道：

```text
有哪些 Consumer
Consumer 在哪
Consumer 用什么语言
Consumer 是否正在升级
```

非常适合：

- 电商订单
- 微服务
- IoT
- 日志处理
- 实时数据系统
- AI 工作流
- 通知系统

---

# 十二、模型 11：实时双向通信

HTTP 通常是：

```text
Client
 ↓
Server

Client
 ↓
Server
```

客户端主动发请求。

但聊天应用希望：

```text
Server
 ↓
主动通知 Client
```

于是有：

```text
Client
 ↕
WebSocket
 ↕
Server
```

一旦连接建立：

```text
Client → Server
Server → Client
```

双方都可以主动发消息。

MDN 将 WebSocket 描述为浏览器与服务器之间的双向交互通信会话，不需要客户端不断轮询服务器。

---

## 典型场景

```text
即时聊天
在线游戏
协同编辑
股票行情
实时通知
外卖配送位置
在线客服
```

---

## SSE

如果主要是：

```text
Server → Client
```

单向推送，也可能使用：

```text
Server-Sent Events
```

例如：

```text
AI 流式输出
服务器日志
通知流
```

所以：

```text
HTTP      请求-响应
SSE       服务端持续推送
WebSocket 双向实时
```

可以先这样理解。

---

# 十三、模型 12：流式系统（Streaming）

有些应用不是：

```text
来一个请求
处理一次
结束
```

而是：

```text
数据
数据
数据
数据
数据
...
```

持续不断产生。

例如：

```text
IoT 传感器
服务器日志
交易数据
用户行为
工业设备
风控事件
```

典型：

```text
Data Source
   ↓
Kafka
   ↓
Stream Processor
   ↓
Flink / Spark Streaming
   ↓
Database / Dashboard / Alert
```

---

## 和普通 CRUD 的区别

CRUD：

```text
有人问我 → 我查数据
```

Streaming：

```text
数据自己不断进入 → 系统不断处理
```

例如温度传感器：

```text
25.1℃
25.3℃
25.8℃
81.2℃
```

系统发现：

```text
> 80℃
```

立即：

```text
触发告警
```

---

# 十四、模型 13：批处理 / 定时任务

还有一种系统甚至不需要客户端触发。

例如：

```text
每天 02:00
 ↓
统计昨天订单
 ↓
生成报表
 ↓
发送邮件
```

或者：

```text
每 10 分钟
 ↓
扫描异常订单
 ↓
执行补偿
```

典型技术：

```text
cron
Spring @Scheduled
Quartz
XXL-JOB
Airflow
```

这类系统是：

> **时间驱动。**

---

# 十五、模型 14：Serverless / FaaS

传统后端：

```text
Spring Boot Server
24 小时运行
```

Serverless 思路：

```text
事件发生
 ↓
运行 Function
 ↓
执行逻辑
 ↓
Function 结束
```

例如：

```text
用户上传图片
 ↓
Object Storage
 ↓
触发 Lambda
 ↓
生成缩略图
 ↓
保存
```

或者：

```text
HTTP Request
 ↓
API Gateway
 ↓
Function
 ↓
Database
```

开发者主要关注：

```text
函数代码
```

而：

```text
服务器
扩容
运行实例
部分基础设施运维
```

交给云平台处理。

---

## 常见平台

```text
AWS Lambda
Azure Functions
Google Cloud Functions
Cloudflare Workers
```

# 十六、模型 15：Edge Computing（边缘计算）

传统：

```text
中国用户
 ↓
美国服务器
```

请求可能跨越很远距离。

Edge：

```text
用户
 ↓
附近的 Edge Node
 ↓
执行一部分逻辑
```

也就是：

> 把计算放到离用户更近的位置。

典型：

```text
Client
 ↓
Edge
 ├── 鉴权
 ├── 缓存
 ├── API 处理
 └── 部分业务逻辑
 ↓
Origin Server
```

Cloudflare Workers 就是典型的边缘 Serverless 平台。

---

## 适合

- 全球应用
- CDN
- API 加速
- 图片处理
- 权限校验
- 低延迟应用
- IoT

---

# 十七、模型 16：P2P（Peer-to-Peer）

经典 Client / Server：

```text
Client A
   ↓
 Server
   ↓
Client B
```

P2P：

```text
Client A
   ↕
Client B
```

两个客户端可以直接通信。

---

## WebRTC

例如视频通话：

```text
Browser A
    ↕
  WebRTC
    ↕
Browser B
```

音视频数据尽可能点对点传输。

但注意：

> P2P 不代表完全没有服务器。

通常仍然需要服务器完成：

```text
身份认证
用户发现
信令交换
NAT 穿透辅助
```

MDN 对 WebRTC 的说明也强调：媒体和数据可以进行点对点交换，但建立连接通常仍需要信令机制。

---

## 典型场景

```text
视频通话
语音通话
P2P 文件传输
BitTorrent
部分区块链网络
```

---

# 十八、模型 17：Offline-First / Local-First

传统云应用：

```text
Client
 ↓
Server
 ↓
Database
```

服务器是数据中心。

如果断网：

```text
应用可能基本不能用
```

Local-first 的思路：

```text
Client
 ↓
Local Database
```

本地先完成操作：

```text
编辑
保存
查询
```

然后有网络时：

```text
Local
 ↕ Sync
Cloud / Other Devices
```

即：

```text
本地数据副本
+
后台同步
+
冲突解决
```

---

## 典型体验

```text
没网也能编辑
 ↓
恢复网络
 ↓
自动同步
```

常见于：

- 笔记
- 文档
- 移动 App
- 协作工具
- 弱网环境应用

Local-first 相关研究强调的核心能力就是：

```text
离线工作
多设备同步
协作
用户对数据拥有更强控制
```

---

AI 应用仍然是 Client / Server，但核心处理流程发生了变化。

传统：

```text
Client
 ↓
Backend
 ↓
Database
```

LLM：

```text
Client
 ↓
Backend
 ↓
LLM
 ↓
Result
```

稍复杂：

```text
User
 ↓
Backend
 ↓
Prompt
 ↓
LLM
 ↓
Tool / Search / Database
 ↓
LLM
 ↓
Response
```

---

## RAG

```text
User Question
 ↓
Embedding / Retrieval
 ↓
Vector Database
 ↓
Relevant Chunks
 ↓
LLM
 ↓
Answer
```

---

## Agent

```text
User Goal
 ↓
Agent
 ↓
Plan / Decide
 ↓
Tool Call
 ↓
Observe Result
 ↓
Decide Again
 ↓
Final Result
```

这时候后端的重要职责不再只是 CRUD，而是：

> **工作流编排。**

# 二十、一个现代大型应用通常是“混合架构”

实际项目基本不会只属于一种模型。

例如一个现代电商 App：

```text
                        ┌→ Redis
                        │
```

# 二十一、从“谁驱动系统运行”来记最清楚

这是我最推荐的记忆方式。

| 驱动方式 | 核心链路 | 常见场景 |
|---|---|---|
| 请求驱动 | Client → Server → Response | CRUD、后台管理 |
| 事件驱动 | Event → Consumers | 微服务、电商、IoT |
| 消息驱动 | Producer → Queue → Worker | 异步任务 |
| 实时连接 | Client ↔ Server | 聊天、游戏 |
| 数据流驱动 | Stream → Processor | 日志、IoT、大数据 |
| 时间驱动 | Scheduler → Job | 报表、清算 |
| P2P | Peer ↔ Peer | 视频、文件传输 |
| 本地状态驱动 | Local DB ↔ Sync | 离线应用 |
| AI 决策驱动 | Input → Model → Tools | Agent、RAG |

# 二十六、一些值得以后再学的高级模式

这些暂时知道名字即可。

## CQRS

把：

```text
写数据 Command
```

和：

```text
查数据 Query
```

拆开。

```text
Write Model
      ≠
Read Model
```

适合复杂、高并发业务。

---

## Event Sourcing

普通系统保存：

```text
当前状态
```

例如：

```text
余额 = 100
```

Event Sourcing 更强调保存：

```text
+100
-20
+50
-30
```

通过所有事件重建：

```text
当前余额 = 100
```

---

## Saga

微服务中一个业务可能横跨：

```text
订单
库存
支付
优惠券
```

Saga 用来协调这种：

> 跨多个服务的长事务。

---

## Choreography / Orchestration

### Orchestration

有一个中央协调者：

```text
Orchestrator
 ├→ A
 ├→ B
 └→ C
```

### Choreography

没有中央导演：

```text
A 发布事件
 ↓
B 响应
 ↓
再发布事件
 ↓
C 响应
```

这两个思想在：

```text
微服务
工作流
Agent
```

中都会不断出现。

# 二十九、一句话总览

可以先把现代应用构建世界压缩成下面这张图：

```text
                    应用
                     │
        ┌────────────┼─────────────┐
        │            │             │
      客户端       服务端          数据
        │            │             │
 Web / App       Monolith       Database
 Desktop          Microservice   Cache
 IoT              Serverless    Object Storage
        │            │
        └────通信────┘
             │
     ┌───────┼─────────┐
     │       │         │
   HTTP     MQ      WebSocket
 REST     Event      SSE
 gRPC     Stream     WebRTC
     │
     ↓
  请求 / 响应
  事件
  消息
  流
  实时推送
  点对点通信
```

如果以后面对一个完全陌生的系统，可以按下面五个问题拆：

```text
1. 谁是 Client？
2. 谁是 Server？
3. 谁主动发起动作？
4. 它们通过什么通信？
5. 状态和数据最终放在哪里？
```

然后再继续问：

```text
6. 哪些操作必须同步？
7. 哪些可以异步？
8. 是否需要实时推送？
9. 是否需要拆服务？
10. 是否需要在本地、边缘或其他节点执行计算？
```

只要这十个问题逐渐能够回答，大多数应用架构图就不会再显得神秘。
