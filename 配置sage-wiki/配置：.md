**进入核心流程**：**初始化 ➡️ 配置硅基流动模型 ➡️ 投放资料 ➡️ 增量编译** 。

初始化：
```
.\sage-wiki.exe init

Project "sage-wiki" initialized. Run: sage-wiki compile --watch
```

当前目录生成知识库骨架：
- **`raw/` 文件夹**：这是你存放原始资料（PDF、Markdown 笔记等）的地方 。
    
- **`sage.yaml` 文件**：这是整个项目的中央配置文件，也是易错点。

配置sage配置文件：
```yaml
#api部分：
api:

  provider: openai-compatible

  api_key: {"硅基流动api"}

  base_url: https://api.siliconflow.cn/v1      # custom endpoint (OpenRouter, Azure, local proxy, etc.)

  rate_limit: 60      # requests per minute (default: auto per provider)
```

```yaml
#请求模型部分，采用deepseek-v4-flash
models:

  summarize: deepseek-ai/DeepSeek-V4-Flash

  extract: deepseek-ai/DeepSeek-V4-Flash

  write: deepseek-ai/DeepSeek-V4-Flash

  lint: deepseek-ai/DeepSeek-V4-Flash

  query: deepseek-ai/DeepSeek-V4-Flash
```

配置`emb` (Embedding，向量模型)，把人类的文字翻译成一串高维度的数字（向量）。
```yaml
#选用Qwen/Qwen3-Embedding-8B
  provider: openai       # auto, openai, gemini, ollama, voyage, mistral

  model: Qwen/Qwen3-Embedding-8B             # override model (e.g., text-embedding-3-small)

  api_key: {xxx}           # separate API key for embeddings

  base_url: https://api.siliconflow.cn/v1           # separate endpoint for embeddings
  
  dims: 4096
```
注意要加上dims维度配置项：
`dims`（Dimensions，维度）:
	向量空间模型（Vector Space Model）中最核心的超参数。配置文件中强制加上 `dims: 4096`，最直观的作用是：它是在向编译引擎声明该向量模型的“数学规格”，以此来建立标准的内存对齐（Memory Alignment）和数据库索引 。

### 1. 成功的部分（Tier 0 & Tier 1）

日志显示：`Indexed: 1 sources (1 embedded)` 。这说明你的本地编译引擎 `sage-wiki` 成功读取了 `raw\Python学习路线与进阶指南.md` ，并且成功调用硅基流动的 **Qwen3-Embedding (emb) 模型**把这篇文章变成了 4096 维的向量 ！**这证明你加的 `dims: 4096` 极其成功，完全没有报维度错误** ！

### 2. 失败的部分（Pass 1: Summarize）

当系统进入 `Pass 1: Summarize` 阶段，准备调用 **DeepSeek-V4-Flash** 去通读全篇并写总结时 ，卡住了 。

- **原因**：`context deadline exceeded` 意思是**连接超时** 。因为你投喂的这篇《Python学习路线与进阶指南.md》内容可能比较长，或者当时硅基流动服务器上调用 DeepSeek-V4-Flash 的人太多、响应太慢 。`sage-wiki` 本地引擎等了太久（超过了它默认的超时限制），不等了，直接断开连接并抛出错误 。
    

所以最终结果是：`0 summarized, 0 concepts, 1 errors` ，你的 `wiki/` 文件夹里现在大概率还是空的。


## 解决：
1.重试，仍失败

2.配置文件中给api调用设定超时时间：
`timeout: 5m`

```

   Cost:   ~$0.0325

分析：
- **Pass 1 顺利过关**：大模型成功读完了你放进去的《Python学习路线与进阶指南.md》，并写出了整篇大纲摘要！
    
- **Pass 2 顺利过关**：DeepSeek 从中精炼地提取出了 **10 个核心概念**（如：基础、数据类型、控制流、面向对象等）。
    
- **Pass 3 斩获 8 项全胜**：在为这 10 个概念分别编写长篇 Wiki 百科文章时，有 **8 篇彻底写完并安全落盘**（生成了对应的 `.md` 笔记文件）。

  报错和警告：
  ```
(1)2个 `context deadline exceeded` 报错（在面向对象、Python高级特性上）

因为 `sage-wiki` 默认是多线程（并发）同时向硅基流动请求写 10 篇文章的。 硅基流动对免费或低等级用户有严格的 **RPM (每分钟请求数)** 和服务器排队限制。那两个概念在请求时，刚好碰上云端服务器拥堵，导致本地等超时了。

解决：再次运行编译，当发现有八篇已完成时，其就会去补齐剩下两篇

(2) 大量的 `low quality article` 警告
这是因为投喂的原始资料《Python学习路线与进阶指南.md》里，可能只提到了这些概念的名字，没有展开写极度详细的代码和细节（比如只是提了一句“要学面向对象编程”）。 `sage-wiki` 严格按照 Karpathy 的理念，**不准大模型瞎编胡话（避免幻觉）**，资料里有多少它就写多少。因为它发现生成的文章太短、覆盖率太低，所以抛出警告说“质量偏低”。这不是错误，只是在提醒你：以后可以往 `raw/` 里面喂更详细、更硬核的原始资料！
  ```
  
  认识缓存机制：当我想通过重新编译获得刚刚失败的两篇文章时：
  ```
  ✓ Nothing to compile — wiki is up to date.
Compile complete: +0 added, ~0 modified, -0 removed, 0 summarized, 0 concepts, 0 articles
  ``` 
  这是因为sage-wiki本地维护了一个**缓存哈希表（State DB / Cache）**，每次编译时都会检查`raw/`中所有文件的 MD5/SHA256 哈希值，并检查这些哈希值是否和上次编译成功时记录下的值相同。
  
  刚刚虽有两个文件生成失败，但此时再运行编译，`raw/` 下的那篇《Python学习路线与进阶指南.md》文件内容没有丝毫变化，hash值也不会变化，sage-wiki就认为没必要再去重新编译。
	 通过微调源文件解决缓存问题：
	 最末尾**随便敲一个空格，或者换个行**，然后保存。改变文件内容就能触发再次编译，且编译时增量编译，它通过对比发现之前有 8 篇概念文章已经存在于 `wiki/` 目录中了，就只会调用deepseek去解决报错的那两篇文章。
	 但不能在中间修改，否则会改变其以编译好的记录，当他监测到中间部分变化时又会将整个文件开始编译，而不是从上次失败的地方，会再次触发并发限制。
