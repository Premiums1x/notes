哈希表： key-value对，哈希表通过哈希算法将key和value实现映射，使用时类似查字典，输入key就能拿到对应value。

- `python`中的实现：`Hashmap: dict={}` 采用开放寻址。字典 dict 使用伪随机数进行探测。
- `Java`：`Map<String,Integer> map = new HashMap()`Java 采用链式地址。自 JDK 1.8 以来，当 HashMap 内数组长度达到 64 且链表长度达到 8 时，链表会转换为红黑树以提升查找性能。

对比数组、链表，哈希表的元素查找、插入、删除效率均为O(1)。

哈希表可以用数组实现，每个元素空间又称为`桶`，其中存储一个键值对，输入一个key，通过哈希函数，`（哈希函数的本质是将一个大的输入空间映射到较小的输出空间,key可以任取，但是数组索引是有限的）`得到对应桶（存储该ey及其对应值）的存储位置，然后从桶中可以取出value，这种情况下，哈希算法一般是`key % len(arr)`，对数组长度取余，就能得到对应桶的位置，

但是数组空间有限，容易出现哈希冲突(多个输入都指向同一个输出)问题。

### 解决哈希冲突：

- 哈希扩容：哈希表容量 越大，多个 key 被分配到同一个桶中的概率就越低，冲突就越少。因此，可以通过扩容哈希表来减少哈希冲突。

缺点：扩容需要将哈希表元素全部迁移，耗时。且需要在新的哈希表计算每个桶的位置。

#### 负载因子：定义为哈希表的元素数量除以桶数量，用于衡量哈希冲突的严重程度，也常作为哈希表扩容的触发条件。

#### 扩容方法效率过于低下，改良方法：1. 改良哈希表结构，冲突时正常工作。 2. 出现严重哈希冲突时才扩容。

### 改良哈希表结构方法：

#### 1. 链式地址：

原先每个数组元素作为“桶”直接存储一个键值对，现在每个“桶”存储一个链表/动态列表，键值对其中的节点，查询时到达头节点然后遍历、删除、更新同理

这种方法空间上因为要存储引用，需要开辟更大存储空间，时间上因为要遍历，时间复杂度为O(n)，耗时长。

当链表很长时，查询效率 很差。此时可以将链表转换为“AVL 树”或“红黑树”，从而将查询操作的时间复杂度O(n)优化至O(logn).

#### 2.开发寻址（不引入额外数据结构）

- 线性探测，规定固定步长线性搜索来探测。 插入时如果发现哈希冲突，则在从该桶往后遍历直到有空位插入。

查找时，遇到哈希冲突，就在该桶往后遍历对比是否相同，若遇到空桶就说明该元素不在哈希表中

但这种方法容易导致数据积聚，且不能在开放寻址哈希表中直接删除元素。这是因为删除元素会在数组内产生一个空桶 None ，而当查询元素时，线性探测到该空桶就会返回，因此在该空桶之下的元素都无法再被访问到，程序可能误判这些元素不存在

*解决该问题，采用懒删除（lazy deletion）机制：它不直接从哈希表中移除元素，而是利用一个常量 TOMBSTONE 来标记这个桶。在该机制下，None 和 TOMBSTONE 都代表空桶，都可以放置键值对。但不同的是，线性探测到 TOMBSTONE 时应该继续遍历*

*懒删除可能会加速哈希表的性能退化。这是因为每次删除操作都会产生一个删除标记，随着 TOMBSTONE 的增加，搜索时间也会增加，因为线性探测可能需要跳过多个 TOMBSTONE 才能找到目标元素。*

为此，*考虑在线性探测中记录遇到的首个 TOMBSTONE 的索引，并将搜索到的目标元素与该 TOMBSTONE 交换位置。这样做的好处是当每次查询或添加元素时，元素会被移动至距离理想位置（探测起始点）更近的桶，从而优化查询效率。*

- 平方探测：跳过“探测次数的平方”的步数，即 1、4、9、16...步。 平方探测主要具有以下优势。

平方探测通过跳过探测次数平方的距离，试图缓解线性探测的聚集效应。 平方探测会跳过更大的距离来寻找空位置，有助于数据分布得更加均匀。 然而，平方探测并不是完美的。

仍然存在聚集现象，即某些位置比其他位置更容易被占用。 由于平方的增长，平方探测可能不会探测整个哈希表，这意味着即使哈希表中有空桶，平方探测也可能无法访问到它。

- 多次哈希： 使用多个哈希函数 f1，f2，f3...进行探测。

插入元素：若哈希函数 f1 出现冲突，则尝试 f2，以此类推，直到找到空位后插入元素。 查找元素：在相同的哈希函数顺序下进行查找，直到找到目标元素时返回；若遇到空位或已尝试所有哈希函数，说明哈希表中不存在该元素，则返回 None 。 与线性探测相比，多次哈希方法不易产生聚集，但多个哈希函数会带来额外的计算量。
